4. RECURRING PATTERNS ESTABLISHED

1. Multi-priority data resolution for cost and price. Every helper now walks at least three sources before returning zero.
2. Frontend defensive layers. When backend changes are pending a rebuild, parallel Angular lookups against existing endpoints make the same data flow visible immediately. The pattern is now in three places: Design Costing service-rate lookup, Design Costing per-unit math fallback, and Dispatch design-costing lookup.
3. Memoise projected lists. Templates iterate plain properties with trackBy. Getters that return new arrays are explicitly banned because they caused a Page Unresponsive earlier this session.
4. Editable computed fields where master data may be sparse (for example Service / Unit). The operator override is always available.
5. Component CSS hygiene. A missing styleUrls is treated as a P1 bug. Four components were silently unstyled during Phase R and three still remain (see Pending items below).

6. DATA QUALITY OBSERVATIONS FROM THIS SESSION

The most expensive bugs of this session were not code bugs. They were silent data gaps that the UI then surfaced as zeros. The new fallback chains reduce the blast radius, but the underlying data hygiene work still matters.

- Seven of eight users had bad CreatedBy or UpdatedBy values (0, 1, 2075 - the last being an EmployeeId confused with a UserId). The data was fixed with a targeted SQL update that only touched broken rows. The GetCurrentUserId fallback to the lowest-id active user should paper over future occurrences.
- The Component Materials table is empty for most designs. The BOM screen displays Gen_BOM (Rpt, Head, Panni, Solv production specs), which is not the same table as Gen_ComponentMaterials (QtyPerUnit by RawItemId). Operators need clearer guidance on which screen drives material costing.
- The Service Rate branch occasionally differs from the Design branch. The frontend lookup added this session bypasses the branch filter, but operations should align them at the data level.
